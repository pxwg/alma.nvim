*alma.nvim* Native Neovim frontend for Alma

Requirements~

Neovim 0.12.0 or newer is required. The local Alma API defaults to:

  http://127.0.0.1:23001

Set `ALMA_API_URL` or pass `api_url` to setup to override it.

Setup~

>lua
  require("alma").setup({
    api_url = vim.env.ALMA_API_URL or "http://127.0.0.1:23001",
  })
<

Commands~

                                                        *:Alma*
`:Alma open [thread_id]` opens the current or requested Alma thread in the
default floating layout.

`:Alma toggle [thread_id]` hides the visible Alma window for the current or
requested thread, or reopens it in the last used layout.

`:Alma float [thread_id]` opens the current or requested Alma thread in a
floating window.

`:Alma sidebar [thread_id]` opens the current or requested Alma thread in a
right-side split.

`:Alma crews` opens the current thread's agent crew summary.

                                                        *:AlmaHealth*
`:AlmaHealth` checks Neovim, curl, and Alma API availability.

                                                        *:AlmaThreadOpen*
`:AlmaThreadOpen {thread_id}` opens a Neovim buffer for one Alma thread.

                                                        *:AlmaSubmit*
`:AlmaSubmit [prompt]` sends a prompt through `/ws/threads`. Without arguments,
it reads the editable bottom `## You` composer in the current Alma buffer.

                                                        *:AlmaStop*
`:AlmaStop` sends a `stop_generation` WebSocket request for the current thread.

                                                        *:AlmaThreads*
`:AlmaThreads` opens the snacks picker thread list.

                                                        *:AlmaModels*
`:AlmaModels` opens model and reasoning selection.

                                                        *:AlmaTools*
`:AlmaTools` toggles tool defaults for the current thread.

                                                        *:AlmaSkills*
`:AlmaSkills` toggles skill defaults for the current thread.

                                                        *:AlmaMCPServers*
`:AlmaMCPServers` toggles MCP server defaults for the current thread.

                                                        *:AlmaEvents*
`:AlmaEvents` opens the raw WebSocket/debug event picker.

                                                        *:AlmaToolDetails*
`:AlmaToolDetails` opens a scratch detail buffer for the block under cursor.

                                                        *:AlmaAgentCrew*
`:AlmaAgentCrew` opens the current thread's native Alma crew timeline. It fetches
`/api/threads/{id}/agent-crew` and renders missions, sprint progress, active
steps, contracts, evaluations, handoffs, and runs. The same data is also shown as
compact virtual progress lines below the bottom composer. `:Alma crews` opens the
same view.

                                                        *:AlmaQuickfix*
`:AlmaQuickfix` extracts file locations from the current thread into quickfix.

                                                        *:AlmaDiff*
`:AlmaDiff` opens patch-like block output in a diff scratch buffer.

Completion~

Use this blink.cmp provider:

>lua
  require("blink.cmp").setup({
    sources = {
      default = { "lsp", "path", "snippets", "buffer", "alma" },
      providers = {
        alma = {
          name = "Alma",
          module = "alma.completion.blink",
        },
      },
    },
  })
<

Token-only prompt lines configure the request:

  /skill:<id>
  @Bash
  @mcp:<server>
  $model:<id>
  $reasoning:low|medium|high|xhigh
  >buffer
  >selection
  >diagnostics
  >diff
  >file:<path>

Extension hooks~

`require("alma.hooks")` exposes generic lifecycle hooks through `on()` and the
alias `register()`. Callback failures are contained with `pcall`, and each hook
dispatch emits a matching `User` autocmd with inspectable `event.data`.

  thread_opened          User AlmaThreadOpened
  thread_changed         User AlmaThreadChanged
  before_submit          User AlmaBeforeSubmit
  request_compiled       User AlmaRequestCompiled
  after_submit           User AlmaAfterSubmit
  generation_completed   User AlmaGenerationCompleted
  generation_error       User AlmaGenerationError
  proposal_received      User AlmaProposalReceived

>lua
  local hooks = require("alma.hooks")
  hooks.on("before_submit", function(event)
    vim.print(event.thread_id)
  end)
<

Context attachments~

`require("alma.context")` stores file or JSON attachments by thread id with
stable id-based dedupe. Pending attachments are appended to the next request's
`ephemeralContext` after `before_submit` hooks and before request compilation.
Inline JSON uses JSON context by default; set `inline = false`,
`file_backed = true`, provide `path`, or set `max_inline_bytes` to use
file-backed JSON context. Request metadata stores compact attachment
labels/counts only. `context.consume(thread_id)` returns registered attachments
and removes those marked `once = true` after a successful local submit dispatch.

>lua
  local context = require("alma.context")
  context.attach("thread-id", {
    type = "json",
    id = "state",
    data = { ready = true },
    once = true,
  })
  local items = context.consume("thread-id")
<

Proposal-like events~

Generic WebSocket payloads whose event name contains "proposal" are normalized
to `proposal_received` with `id`, `thread_id`, `kind`, `title`,
`base_snapshot_id`, `files`, and `raw` before `User AlmaProposalReceived`.

Reliability~

alma.nvim turns the bottom `## You` composer into the sent user message,
renders one loading Alma response, and locks the buffer while generation is in
flight. If the same thread is already generating, the request is queued in
Neovim and visibly marked as queued. Generation completion or failure always
reconciles through REST messages.
